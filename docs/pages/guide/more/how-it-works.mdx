# How it works

## The problem

Typical drag-and-drop libraries find the drop position by calling `getBoundingClientRect()` on sibling elements. A virtual list renders only the rows in view, so most siblings do not exist and that approach breaks.

## Geometric hit-testing

When a drag starts, ngx-virtual-dnd records the drop targets in the active group and their bounding rectangles. On each pointer move it compares the pointer position with those cached rectangles, instead of asking the browser which element is under the pointer. This avoids forcing a layout recalculation on every frame of the drag.

The cache updates itself:

- Rectangles are re-read after a scroll or resize, when a target resizes (through `ResizeObserver`), and when a target moves without resizing.
- Targets mounted or removed during the drag are added or dropped.
- Disabled and hidden targets are skipped.
- Each rectangle is clipped to the `vdndScrollable` elements around it, minus the space their [scroll insets](/guide/features/page-scroll#sticky-headers-and-footers) cover, so a list scrolled out of view, or behind a sticky header, cannot be hit. A scroll container that is not marked `vdndScrollable` doesn't clip the lists in it.

When rectangles overlap, the last one in document order wins.

## Placeholder math

Once the target list is known, the drop index comes from arithmetic, not DOM queries:

- The probe point is the dragged preview's center, capped at half an item below the preview's top edge, so tall items do not jump ahead of the pointer.
- **Fixed heights:** the index is `floor((probeY - listTop + scrollTop) / itemHeight)`.
- **Dynamic heights:** a binary search over prefix sums of measured heights finds the row under the probe. The placeholder only moves past that row once the preview's top edge crosses the row's midpoint, so a short item entering a tall row needs half of that row's height.

While an item is dragged within its own list it is hidden with `display: none` and the placeholder takes its slot. The list's total height stays the same, so content below the list does not shift. The index calculation accounts for the hidden item, so the logical position stays correct.

## Rendering

Pointer moves are coalesced into a single `requestAnimationFrame` loop that reads layout, computes the new state and then writes styles, in that order. Drag state lives in signals, so only the parts of the page that depend on it update. The loop and all high-frequency listeners run outside Angular's zone. The `dragStart`, `dragEnd` and `drop` outputs are emitted inside it, so handlers that change plain fields still render in zone.js apps.

A scroll renders its rows in the scroll event, which the browser dispatches in the frame that first shows the new position, before it lays out and paints that frame. Rendered any later, a fast scroll would paint that frame with the rows of the previous position, blank wherever it moved past the overscan. A resize renders in the `ResizeObserver` callback that reports it, after the frame's layout and before its paint: a list shown again (in a tab, an accordion) gets the rows of the scroll position the browser restored, and a taller list or a taller header above `<vdnd-virtual-content>` the rows that come into view. When the items shrink to end above the scroll position (a filter), the list renders its last rows right away, where the browser is about to move the scroll position. Only the rows that came into range are created or checked.

## Row recycling

`<vdnd-sortable-list>` and `<vdnd-virtual-scroll>` can reuse the view of a row that scrolls out to render a row that scrolls in, and `*vdndVirtualFor` always does. See [Row recycling](/guide/features/performance#row-recycling) for what that means for your row components.

## Browser support

The latest versions of Chrome, Edge, Firefox and Safari, on desktop and mobile. Every change runs the end-to-end suite in Chromium, Firefox and WebKit, with mobile touch runs in Chromium and WebKit.
